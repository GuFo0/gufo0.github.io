4. Conceptual Foundations: Taxonomy of Cryptographic Primitives

To understand the Ethereum wallet architecture, we must distinguish between five fundamentally different mathematical concepts:

Category Representative Standard Mathematical Purpose Reversibility & Security
Key Generation CSPRNG (OS Entropy) Generates true, uncorrelated cryptographic randomness (128–256 bits). Non-deterministic; requires hardware/OS noise.
Key Derivation BIP-32 / BIP-44 (HMAC-SHA512) Expands one single seed deterministically into an infinite tree of child keys. Deterministic pseudo-random expansion; irreversible without parent key.
Public-Key Crypto secp256k1 (ECDSA) Asymmetric one-way trapdoor function (Q = kG) enabling digital signatures. Forward is trivial; inverse (ECDLP) is computationally impossible.
Hashing Keccak-256 Fixed-size compression (maps arbitrary input to uniform 256-bit output). Strictly one-way, non-algebraic, collision & pre-image resistant.
Checksums EIP-55 (Mixed-Case) Error-detecting code designed to catch human typos and transcription errors. Not designed to resist malicious attackers; targets accidental bit flips.
Encoding Hexadecimal (0x...) Transforms raw binary bytes into a human-readable text format. 100% reversible; provides zero cryptographic security.

5. Temporal and Historical Context

The cryptographic tools used by Ethereum were not invented at the same time. They represent nearly 40 years of evolving cryptographic research:

1977 • RSA Algorithm
First Practical Public-Key Cryptography (Rivest, Shamir, Adleman)

Introduced the revolution of asymmetric cryptography based on the hardness of factoring large composite primes.

2001 • SHA-2 (SHA-512)
NIST FIPS 180-2 Standard

Standardized the Merkle-Damgård hash family. SHA-512 is used today inside BIP-39 (PBKDF2) and BIP-32 (HMAC).

2012 • BIP-32
Hierarchical Deterministic (HD) Wallets (Pieter Wuille)

Eliminated the danger of backing up every new private key individually by introducing master seed derivation trees.

2013 • BIP-39
Mnemonic Words for Deterministic Wallets (Marek Palatinus et al.)

Solved human usability by encoding raw binary entropy into 12 or 24 human-readable dictionary words with checksum verification.

2014 • BIP-44
Multi-Account Hierarchy Standard (Palatinus, Rusnak)

Standardized the path m / purpose' / coin_type' / account' / change / address_index, assigning coin type 60' to Ethereum.

2015 • SHA-3 (NIST FIPS 202)
Standardization of Keccak Sponge Construction

Standardized the sponge function designed by Bertoni, Daemen, Peeters, and Van Assche after the NIST competition.

2016 • EIP-55
Mixed-Case Checksum Address Encoding (Vitalik Buterin)

Added checksum protection to Ethereum addresses by capitalizing letters based on Keccak-256, maintaining 100% backwards compatibility with legacy hex parsers.

6. SHA-2 vs. Keccak-256 vs. NIST SHA-3

1. Merkle-Damgård vs. Sponge Construction:
SHA-2 uses Merkle-Damgård compression, which is vulnerable to length-extension attacks. Keccak uses an innovative Sponge Construction that absorbs data into a state and squeezes it out, entirely preventing length-extension.

2. Why Ethereum's Keccak-256 is NOT identical to NIST SHA3-256:
In 2014, Ethereum adopted Keccak-256 as submitted to the NIST competition with padding byte 0x01. In 2015, when NIST finalized FIPS 202, they changed the domain separation padding byte to 0x06. Thus:
• Keccak-256("") = c5d2460186... (Used in Ethereum)
• SHA3-256("") = a7ffc6f8bf... (NIST Standard)
Ethereum maintains original Keccak-256 for consensus consistency.

7. Why Multiple Primitives Instead of One?

The Principle of Cryptographic Separation of Concerns:
No single algorithm can simultaneously solve backup usability, non-repudiation signatures, address compression, and typo detection:

  • BIP-39 / BIP-32 / BIP-44: Solves human error and key backup. One 12-word seed recovers all accounts across multiple blockchains.
  • secp256k1: Solves identity and authorization. Digital signatures (ECDSA) require asymmetric algebra (Q = kG) that cannot be performed by hash functions.
  • Keccak-256: Solves compression and privacy. Compressing a 64-byte public key to a 20-byte address saves precious blockchain state storage.
  • EIP-55: Solves safety. Protects human operators from copy-paste truncation and transcription errors without modifying EVM consensus rules.
